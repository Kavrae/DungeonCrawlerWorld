# CLAUDE.md

Guidance for Claude Code in this repo.

## Git
Local, read-only inspection/comparison commands (`git status`, `git diff`, `git log`, and similar) are allowed. Do not run anything that writes to the repo or touches a remote — `add`, `commit`, `push`, `fetch`, `pull`, `stash`, `reset`, `checkout`/`restore`, branch/tag creation or deletion, etc. Leave those to the user.

```
dotnet build DungeonCrawlerWorld.sln
dotnet test Tests/Tests.csproj
dotnet test Tests/Tests.csproj --filter "FullyQualifiedName~ClassName.MethodName"
dotnet test Tests/Tests.csproj --filter "TestCategory=Performance"
dotnet run --project DungeonCrawlerWorld/DungeonCrawlerWorld.csproj
```

- net10.0, Nullable enabled, LangVersion latest, all projects. Nullable warnings are build errors (root `Directory.Build.props`): a non-nullable type is the guarantee a dependency is present, so internal code takes it as non-nullable with no runtime null guard. Drive them through the `phase-performance-testing` skill, which also does before/after A/B runs.

## Layers (one-way deps)
`Engine → Game → Presentation → DungeonCrawlerWorld(exe)`
- **Engine**: generic ECS + modding infra. No game-specific knowledge.
- **Game**: world/map, blueprints (entity templates), built-in modules (Core, Movement, Health, Energy, Race, Class).
- **Presentation**: FNA (XNA-compat) rendering + window/UI. No gameplay logic.
- **DungeonCrawlerWorld**: exe. `GameLoop.cs` = composition root. `WorldSessionBootstrapper.cs` = the game session plus what only the app owns (`WorldSessionContext`: `GameSession`, player activity log, `AdminTools`, reserved entity ids). `ShellBootstrapper.cs` = construction and layout only -- no behaviour lambdas; rules between windows live in Presentation (e.g. `ItemWindowCoordinator`). `ElementFactoryRegistry.cs` = pooled element factories. `Presentation/Input/UiInputController.cs` = input.
- **Game → outside it**: `GameBootstrapper.Build` returns a `GameSession` (`Game.Bootstrap`), built by name from the build's `GameModuleContext`, which stays the modules' build-phase API and is never handed out. `Catalogs` (action, item, loot box, achievement, status-effect display, terrain, blueprint), `SimulationClock`, `Views` (`GameViews`: read-only, per-session views in `Game.Views` -- map, inventory, shop, currency, hotkey bindings, health, stat modifiers, ability scores, action state, transforms, naming), `Commands` (`GameCommands`: per-session write services in their feature's namespace -- `InventoryCommands`, `CurrencyCommands`, `ShopCommands`, `HotkeyBindingCommands`, `LootboxCommands`, `LootCommands`, `PlayerCommands`), `Internals` (factory, skeletons, rebuilder, teleporter, tier resolver, roster, moved entities). A service holds its own pools, catalog, bus and player, so a caller passes only ids and values. Each wraps the feature's static `*Actions`/`*Queries`, which stay the implementation because systems call them with pools of their own. A new outside-of-Game read or write is a method on a view or command, not a new pool handed to Presentation.
- **Content**: copies `Content/Fonts/*.ttf` to output only; not a compiled MonoGame pipeline.
- **Mods.ExampleMod**: real mod pattern — refs Engine/Game with `Private="false"` (no duplicate copies shipped). **Mods.TestFixtures**: mod DLLs for ModuleLoader failure-path tests.

## ECS (Engine/ECS)
- `EcsContext` = EntityManager + ComponentManager + SystemManager + EventBus. Built by `EcsBuilder`'s stages, each a type that can only be advanced once and only in order: `EcsBuilder.Begin(modules, settings, ...)` (checks every module's `Requires`, sorts by `RunsAfter`/`RunsBefore` keeping the caller's order where unconstrained) → `SortedModules.RegisterComponents()` → `RegisteredComponents.Configure(context)` → `ConfiguredModules.RegisterBehavior()` → `RegisteredBehavior.Complete()`. Each phase runs for every module before the next: ALL components before any `Configure`, every `Configure` before ANY systems. Systems run in that order, and so do event subscriptions made in `RegisterBehavior` (e.g. Health's `StatModifierExpiredEvent` handler before AbilityScores').
- Pools: `RegisterDirectPool/RegisterPackedPool/RegisterMultiPool`, each with `MergeAction<T>`. Blueprints always `Merge` not `Add` (composable, no collision throw).
- Systems: `ISystem` + `StripeCount`. `SystemManager` runs every system every frame; each processes only `Count/StripeCount` of its pop per call (entity striping, flat per-frame cost vs periodic-system spikes). `EntityStripeSet` buckets by `entityId % StripeCount`, updated incrementally via EntityAdded/EntityRemoved (no rescan).
- Tiered systems: `TieredEntityStripeSet` = one `EntityStripeSet` per processing tier (Local/Neighborhood/Borough/Beyond), bucket stripe count = base `StripeCount` × tier divisor (`ProcessingTierDivisors`, `ushort` — `byte` silently truncated before). A tiered system implements `ITieredSystem`: expose `Tiers`, per-entity work in `UpdateBucket(time, entityIds, framesPerVisit)`, per-frame work in `BeginFrame`, and `Update` must be exactly `=> TieredSystemRunner.Run(this, time)`. `SystemManager` owns the tier loop and never calls a tiered system's `Update` — anything else put in `Update` is silently skipped. `SystemManager.SimulatedTierCount` = which tiers run at all (game-injected policy; P2 hook).
- Entity ids are recycled the moment an entity is destroyed. Anything that refers to another entity beyond the current frame holds its `EntityKey` (`EntityManager.Keys`, issued once, never reused), not its id. Modules take the key table from `GameModuleContext.EntityKeys` (the EntityManager's own) and pass it to `ActionSource.FromEntity`. Holders: `ActionSource` (8 bytes: kind, key, and an `EntityIdentities` handle for the name and crawler number it had) and `DeadComponent.KilledBy`. Compare a source with the player through `IPlayerQuery.PlayerEntityKey`/`source.IsEntity`, and display it through `source.Identity`. `EntityManager.EntityDestroying` fires before components are removed: `GameBuildPass` clears aura sources, map footprint and tier membership there, `ShellBootstrapper` clears UI selections (the inspected entity, and `ItemWindowCoordinator.ReleaseEntity` for item windows) -- state kept outside the pools about an entity must let go there too. `SystemManager.RegisterFirst` runs a system before everything registered so far.
- **Scale every time-based field by `framesPerVisit`, never a constant.** A coarse-tier entity is visited every `StripeCount × divisor` frames, so a value advanced by 1 (or by base `StripeCount`) per visit moves at a fraction of real time. This defect recurred across ~6 systems before the loop moved into `SystemManager`. It no longer applies to timers at all — those are deadlines now (see the Timers bullet), which is what made the whole class of bug go away; it still applies to anything else a tiered system accumulates per visit, e.g. `ComplexHealthRegenSystem`'s regen amount.
- Timers: **nothing decrements a countdown any more.** Store `FrameDeadline.After(now, frames)` as a `uint` frame and compare against `EngineTime.FrameCount` (in systems) or `SimulationClock.CurrentFrame` (elsewhere; `GameModuleContext.SimulationClock`, advanced by `SystemManager.Update`). Two shapes, by what reaching the deadline means:
  - **Something happens** (a damage tick, an expiry, a windup resolving) → the component implements `IScheduledTimer` (or `IKeyedScheduledTimer` for a Multi pool, keyed by a stable instance id) and its owning system drives a `PackedTimerWheel`/`MultiTimerWheel`. Scheduling is automatic: the wheel observes the pool's `ComponentChanged`, so any normal write of `NextTickFrame` schedules it and no caller has to remember. Re-arm a periodic timer with `timer.RepeatEvery(period)` on the `ref` a pool updater hands you (`ScheduledTimerExtensions`) -- it counts from the deadline that fired, so the cadence stays exact if a firing was ever late, and there is no `now` to pass wrongly. `FrameDeadline.Never` parks a timer (permanent modifiers/immunities are never scheduled).
  - **Nothing happens, it just stops gating** (action lock, movement backoff, regen lockout) → a plain `uint` field and a comparison at the reader. No system, no wheel, no per-entity cost at all.
  - Anything that writes a timer takes `now` as a required parameter rather than reading an ambient clock, so a test can't silently disagree with the frame the system is running on.
- Choosing a shape: no per-entity population (event queues) → plain `ISystem`, no stripe set. Must react the frame something was queued (player input, deaths, dodge windows) → plain `EntityStripeSet`, don't tier. Otherwise → `ITieredSystem`. Two different tiered passes (`StatusEffectAuraSystem`) or event-driven (`ProcessingTierSystem`) → plain `ISystem` running its own loops.
- Tiers are decided by `ProcessingTierResolver` (Game), event-driven by `ProcessingTierSystem` — no periodic scan. Local = Chebyshev radius 80 on the player's layer; otherwise the entity's 1024² neighborhood (`Game.World.Neighborhoods`, shift/mask, floors negatives) decides: the window centre's = Neighborhood, the 8 around it = Borough (frozen, `SimulatedTierCount = 2`), further = Beyond. The centre (`ProcessingTierResolver.WindowCenter`) follows the player's neighborhood once they are 64 tiles past its edge (`WindowShifted`). Every positioned entity is tiered, not just movers. Entities are born tiered: `ProcessingTierResolver.CreateEntityAt` writes the tier as the first component, before the blueprint adds pooled components (stripe sets read it in `OnMemberAdded`); `World.EntityPlaced` → `EnsureTiered` is the catch-all for other placements. An untiered entity fails open to Beyond in every stripe set. Player pinned Local once at spawn.

## Modding (Engine.Modules)
- `IModule` = identity `Guid Id` + three lists of other modules' Ids + the phases that need no context: `DeclareSettings` (default no-op) and `RegisterComponents(ComponentRegistration)`. `IModule<TContext>` adds `Configure(TContext)` (default no-op) and `RegisterBehavior(BehaviorRegistration<TContext>)`, which carries the same context -- so a module keeps no fields between phases, and `Configure` only fills what another module's `RegisterBehavior` reads (catalogs, registries). `RegisterBehavior` wires everything a module runs -- systems, event handlers, and setup that decides which systems exist (Achievements' triggers decide whether `AchievementPollingSystem` is registered) -- after every `Configure`, so no catalog is still filling; never subscribe or read another module's catalog in `Configure`. `IGameModule` = `IModule<GameModuleContext>`. `Requires` (must be present -- presence only, no order), `RunsAfter`/`RunsBefore` (system order only; an absent target is ignored). Requiring never implies order: every component registers before any `Configure` or system, so another module's pool is there whatever the order. A built-in declares `public static readonly Guid ModuleId` and `Id => ModuleId`; dependents name it as `HealthModule.ModuleId`, so a mod replacing it by Id still satisfies them. Mutual `Requires` is fine; a `RunsAfter`/`RunsBefore` cycle throws naming every link and the module and list that declared it (e.g. "Movement runs after Core (Core.RunsBefore)").
- Settings (Engine.Settings): a module declares typed `SettingKey<T>`s (owned by its `Id`, so a replacement takes them over) in `DeclareSettings`; `SettingsCatalog.Declare(modules).Resolve(sources)` gives frozen `SettingValues` plus a `SettingsFailure` per rejected override (unknown key, bad value, malformed entry). Every setting is startup-scoped and readable in every phase; `CommandLineSettingsSource` reads `--setting=ModuleName.SettingName=Value`. Settings may size and tune pools but never decide whether a built-in pool exists. No module declares one yet.
- `ModuleLoader.LoadFromDirectory<TContext>`: reflects `*.dll` into collectible `AssemblyLoadContext`s and returns a `ModuleFactory<TContext>` per public concrete `IModule<TContext>` (each constructed once while loading, so a type that won't construct is reported then). Per-DLL/type failures caught → `ModuleFailure`, never aborts whole load.
- `ModuleSet.Combine`: merges built-ins + mods, replaces built-in by `Id` match. A replacement takes the replaced module's place in the order and must keep its contract: it registers every component type the built-in did, as the same pool kind (more is fine, and it may register no systems). Partial replacement is a TODO.
- Every build is a self-contained `Game.Bootstrap.GameBuildPass.Run`: fresh module instances from factories, its own World over its own Map, EventBus, key table, MathUtility and context -- nothing one build creates is reachable from another, and none depends on running before or after another. After `RegisterComponents` it builds the World and the `GameModuleContext` from the registered pools, so every context member (resolver, simulation scope, floating-text feed, entity factory) is complete from construction -- no `Wire`/late setter anywhere. That makes every build need `GameModuleContext.FoundationModuleIds` (Core, ProcessingTier, Blueprints), checked with a named error. After `RegisterBehavior`: `SpawnMoves` first, skeleton access guard, destruction handlers, the simulation-resume subscription, the clock, the `LocalTierRoster`. `GameBuildPass.BuildModules` is the module build alone, for a test of a few modules.
- `ModValidation.Validate(modsDirectory, settingsSources)` → `ValidatedMods`: loads mods, checks the replacement contract, and trial-builds each (with the built-ins only) in its own pass over `GameBuildPass.CreatePlaceholderMap()`; drop on throw. The game-start / mods-changed step. `GameBootstrapper.Build(validatedMods, map, ...)` = the new-game / load step: the session's pass over `map` plus the `SpawnRecordRebuilder` staging pass, returning a `GameSession`. `BuiltInModules()` lists the built-ins as factories. Load and settings failures only reach `Console.Error` today.
- Built-in pools are always there in a game (mods can only add or replace modules, and a replacement keeps the components), so code always fetches another built-in's pool with `Get*Pool` -- never `IsRegistered` or a nullable pool. A module that fetches another module's pool in `RegisterBehavior` declares it in `Requires`; `BuiltInModulesTests.EveryBuiltInModule_BuildsWithOnlyWhatItRequires` fails otherwise. `BuiltInModulesTests` also pins every system's run order -- a change to it should be deliberate.
- Dependencies point from a feature to what it builds on, never back. A status effect acts on health only through Health's API (`HealthDamage`, `HealthHeal`, `BodyPartDamageEffects` -- e.g. Burning locks a burning part out of regen with `ResetRegenLockout`), and Health never reads a status effect's components; Poison is the model.
- Tests: `BuiltInTestComponents.RegisterAll` (every built-in pool on a bare `ComponentManager`), `BuiltInTestModules.Build(map)` (the whole built-in module set as one `GameBuildPass`), `BuiltInTestModules.BuildModules(modules)` (a few modules alone, foundation modules added), `TestWorlds.Create`/`Over` (a World without the modules), `TestModuleRegistration` (one module's `RegisterComponents` on a bare `ComponentManager`, default settings), `EmptyPools` (stand-ins for pools a test doesn't exercise), and `TestSystems`/`TestHealth`/`TestActionEffects` (the old optional signatures, filling in `EmptyPools`).

## Diagnostics (Engine.Diagnostics)
- **Emit, never thread.** Measured code reads a static `EngineHooks` channel -- `FrameCosts`, `SimulationFrames`, `Sessions`, `DiagnosticScopes` -- and does nothing else when its `Listener` is null. Never pass a recorder, profiler or `DiagnosticsEngine` into the code it measures. Each channel holds one listener (subscribing a second throws); `DiagnosticsEngine.Start()` subscribes whatever its features need (`GameLoop`'s constructor, `HeadlessBenchmark`) and fans out internally, `Dispose` unsubscribes. Channels are process-wide: a test that subscribes is `[DoNotParallelize]`.
- `SystemManager.Update` is the one frame boundary (`SimulationFrames`); a host calls only `EcsContext.Update`. The benchmark window, the "GameLoop" / "EcsContext.Update (all systems)" row, startup stability, memory/leak sampling and the 5 s `latest.json` report all run from it, so they pause with the simulation. Keep benchmark row names stable -- the benchmark skill and saved results read them.
- `EcsContext.BeginSession()` marks the build a host simulates (the last step of `WorldSessionBootstrapper`); disposing it -- through `WorldSessionContext` -- ends it. Trial and staging builds never begin one. Memory and LeakDetection trackers are per session.
- A frame cost at a site that runs a few times a frame is `using (EngineHooks.FrameCost(category, group, item))`. A per-system or per-event path (`SystemManager.Update`, `EventBus.Publish`) branches on `EngineHooks.FrameCosts.Listener` itself instead, so with nothing listening it runs as a bare call -- no try/finally, no arguments evaluated.
- A startup step or build phase worth timing is `using (EngineHooks.DiagnosticScope("Name", detail))`: a constant name, and a detail the caller already holds (a module's `Name`), never a string built for it. `EcsBuilder`'s stages and each module's phase emit them; `StartupProfiler` records them nested until the first simulation frame.
- A value worth watching over time is a gauge: `EcsContext.Gauges.Register(group, name, kind, read)` while building the session (frozen at `BeginSession`, cleared on dispose), registered where the value lives (`EcsContext` for entities/pools, `GameBuildPass.Run` for creatures/tiers, `WorldSessionBootstrapper` for the streamer; process GC figures are `GaugeTracker.ProcessGauges`). Constant names; a "...Bytes"/"...Milliseconds" suffix sets the unit shown. `Level` for a value, `Cumulative` for a counter (sampled as its change per frame). `read` runs at frame end inside `SystemManager.Update`: it reads a counter its owner keeps, never a pool. With `--diagnostics=gauges` they're sampled every frame (`GaugeTracker`), written per benchmark range (`gauges-*.json`), per report interval (`latest.json`), and shown live in the F3 Diagnostics window (`GaugeHistory`).
- Anything that compares against "every living entity" reads `EcsContext.EntityPopulations` first: the game's split into skeleton-held types (every living entity) and everything else (built entities only). `LeakDetector` compares each pool against the population that can hold it.

## World & Map (Game.World)
- `World : IMapQuery` owns `Map` + placement (`PlaceEntityOnMap`/`MoveEntity`/`RemoveEntityFromMap`).
- `Map`: per-cell stores split per 1024² neighborhood (`MapNeighborhood`; world coordinates in, shift/mask inside) — blocking occupant and occupant index per `(x,y,MapLayer)`, terrain per `(x,y,TerrainLayer)`, structures (walls) per `(x,y,MapLayer)`; terrain and structures are `TerrainCell` flyweights from `TerrainRegistry`. Sparse per-cell grids (`AuraGrid`, `MapTintGrid`) use `NeighborhoodCells<T>`. `Map.Bounds` (`Engine.Math.MapBounds`, min inclusive, max exclusive) can start anywhere, negative included, on a neighborhood boundary. The default map is `Map.Unbounded`: whichever neighborhoods are loaded (a dictionary plus a 5x5 lookup grid re-centred with the window), starting with the 3x3 around (0,0); `Bounds` is only the rectangle around them, so test cells with `Contains`. `--map-size=` other than 3072 builds a bounded, fully loaded map with no window. An entity not on the map sits at `TransformComponent.UnplacedOn(layer)`, far outside any map -- never (0,0) or (-1,-1), which are real tiles.
- Map occupancy is governed by `IMapQuery.IsBlocking`, implemented on `World` from two `MultiComponentPool` markers — `ForceBlockingComponent` (wins if present) then `NonBlockingComponent`, else default blocking; both are many-source/count-based so overlapping sources (assumed for all effects) work correctly. `NonBlockingComponent.Kind` (`NonBlockingKind` flags: `Tiny`/`Phasing`) is how `MapWindow` renders the entity while exempt (tiny-grid/phasing-alpha) — folded into the same component that grants the exemption itself (not a separate component), so the two can't drift apart the way they once did. Non-Blocking entities are indexed by position in `Map`'s own `GetNonBlockingEntityIdsAt` (kept in sync by `World`'s placement/move/removal, mirroring the Blocking array) — `MapWindow`, `SelectionWindowContent`, and `AbilityEffectResolver` all query it instead of scanning every non-Blocking entity.
- `FloorBuilder`: `CreateMap` builds the Map `GameBootstrapper.Build` takes (the build makes the World over it); `PopulateFloor` needs EntityManager/ComponentManager from Build. Real ordering constraint. A neighborhood is generated in two halves: `TestMapBuilder.Plan` decides it as data (a `NeighborhoodPlan`: layout in its own detached `NeighborhoodLayout` stores, each row's aura-radiating terrain, the spawn list) from its `NeighborhoodRecord` alone -- layout from its seed, population from a per-visit seed -- touching no pool, map or event, so it runs on a worker; the main thread then `Map.LoadNeighborhood(layout)` and spawns the list in order. Startup plans every window neighborhood in parallel and applies them in order. The hallway cross, fixtures, shops and spawn live in neighborhood (0,0) only. At runtime `Game.Floors.NeighborhoodStreamer` (first system in the frame) unloads a neighborhood (destroys its entities, announces its terrain row by row with `TerrainUnloadingEvent`, `Map.UnloadNeighborhood`) and loads one (planned on a worker from the moment it is queued; applied no earlier than `StartDelayFrames` (30) streamer updates later, waiting for the worker if needed, so streaming stays deterministic: load the stores, `TerrainLoadedEvent` per row carrying its aura cells, then population) under a per-frame budget. A load dropped before it starts cancels its worker and counts no population on its record. It drives the sliding window on `WindowShifted` (loads nearest-first, a cache of the 3 most recently dropped neighborhoods, evictions unloaded before loads) and Admin Mode's map context menu "Regenerate". Unloaded cells are off the map: `Map.Contains`/`World.IsOnMap` false, readers empty.

## Blueprints (Game.Blueprints)
- `BlueprintDefinition` = one composable building block: Guid `Id`, `Name`, ordered `Includes` (other definitions by Guid, built first, nested to any depth), an optional `Build` step (`Action<BlueprintContext>`), and facets: `Race` (body plan; grants `RaceSlotsComponent`), `Class` (granted through `ClassEffects`), `Appearance` (`AppearanceFacet`), `NonBlocking`, `Actions`, default `Layer`/`Size`. Rule: what must be known without building goes on the definition; `Build` writes only the per-entity state a build creates. Every blueprint is a `static class` declaring `Id`, `Name` and its whole `Definition` (after the static fields it uses); a build step is its own `private static void Build(BlueprintContext)`, referenced as `Build = Build`, and a pure composition leaves `Build` null. Pure compositions (`Player`, `GoblinForeman`, fixtures) live in `Composites/`; `BlueprintsModule` registers the built-ins. A static step can hold no state: everything a build depends on arrives in `BlueprintContext` (`ComponentManager`, entity id, `Rolls`, `EntityKeys`, seed, registry), so one method serves every world and every seed.
- `BlueprintRegistry`: session-local `ushort` ids, Guid lookup, re-registering a Guid replaces in place (how a mod replaces a built-in, and every composite including it follows); `Races`/`Classes` are kind views over the one id space. `Resolve` flattens includes depth-first into a cached `ResolvedBlueprint` -- build order (a definition reached twice builds once), races, classes, merged `Actions` (a later grant of an action replaces an earlier one), `EntityAppearance`, occupancy, default layer/size. Cycles, missing includes and nesting past 8 throw; `ResolveAll` runs at the end of module configuration, so a broken mod fails its dry run. Appearance, layer and size: each set field replaces what came before, except a second race's are ignored (a hybrid is its first race). Name = an explicit `Name` if any, else the seeded display name, then each class's name and `NameSuffix`. `Compose(Guid...)` interns an unnamed composite under a Guid derived from its ordered includes.
- To be spawned, a blueprint must resolve a name, description, glyph and a sprite declaration (`AppearanceFacet.NoSprite` = glyph only) -- `ResolvedBlueprint.IsSpawnable`; a trait (Boss, Tiny) doesn't, and is only ever included or applied. These are read from the blueprint through the spawn record (`MapViewQuery`, `EntityNaming`), never stored per entity: `DisplayTextComponent`/`GlyphComponent`/`SpriteComponent` mean a per-instance override (a destroyed container).
- Spawning (Game.Spawning): every entity is spawned by the session's one `EntityFactory` through `Spawn(SpawnRequest)` -- blueprint id and x/y, optionally layer, size, seed, `Crawler` and a reserved id (the player); layer and size default to the blueprint's, seed to the factory's own runtime sequence (population always passes its own). It creates the entity tier-first, builds it (per part in build order: race/class facet, then its `Build`) or defers it to a skeleton, places it, records its spawn move and destroys it if it landed off the map. Every entity carries a `SpawnRecordComponent` (blueprint id, `SpawnFlags`, seed -- 8 B, the flags byte sits in what was padding; Direct pool). Building is in two halves: `BuildSkeleton` writes the skeleton from definitions (see Skeletons below), `BuildComplete` runs every part in build order (race/class facet, then its `Build`), the action-lock stagger, and gives a `SpawnFlags.Crawler` entity its crawler number -- on first build, not at spawn, so an unbuilt crawler never draws one (the allocator has its own sequence seeded from the session seed, so drawing at promotion shifts nothing else). `BuildComplete` reseeds one `SeededRandom` per entity -- a blueprint must draw every random choice from `BlueprintContext.Rolls`, never from a sequence of its own, or the record stops reproducing the entity (`SpawnRecordRebuilder` rebuilds it in a staging world against the session's registry; `SpawnRecordRebuilderTests` guards this). The building itself is `EntityBuilder`'s (definitions, key table, rolls -- no world, tiers or clock), which is what `SpawnRecordRebuilder` uses; `EntityFactory` builds through one and adds placement, tiering, skeletons, spawn moves and crawler numbers.
- `SpawnMoves` (registered first in the frame) records a spawn's move this frame if the moves are still unread, otherwise first thing next frame -- so spawning from a system mid-frame, or from Presentation between frames, is safe. Modules reach the factory as `GameModuleContext.EntityFactory` (built with the context): spawn only once the build is complete, since blueprints resolve after every `Configure`.
- `EntityFactory.Apply(entity, blueprint)` layers a blueprint onto a live entity (a class it gains, a curse): builds a skeleton first, skips any part the entity already has -- one its spawn blueprint built or one applied before -- and records each part it builds as an `AppliedBlueprintComponent` (Multi pool, with its application order). So nothing is ever built onto an entity twice (a merge policy never merges a part into itself; Boss twice doubles health once). Spawn record + applied list = everything the entity was built from: applied parts' actions, class names and name suffixes are read through the list; the rest of an applied part's appearance doesn't change the entity's; the spawn record is untouched. Admin Mode's map context menu offers "Spawn here >" and "Apply >" (`Game.Admin.BlueprintAdminCommands`) -- keep them, they are the in-game test tool.
- `EntityActions` resolves an action from the entity's own `ActionInstanceComponent`, then its applied parts (most recently applied first), then its spawn blueprint's merged grants -- composition's rule, a later part's grant replacing an earlier one. Class slots are not read for actions: every runtime class arrives through `Apply`.
- Skeletons: a creature born into an unsimulated tier is spawned as a skeleton (`CreatureSkeletons`) -- only the types in `EntityFactory.SkeletonComponentTypes`: `TransformComponent`, `ProcessingTierComponent`, `SpawnRecordComponent` and occupancy (`NonBlockingComponent`/`ForceBlockingComponent`). A type goes on that list only if its value is declared on the definition or set by the spawn, and something needs it on unbuilt entities; `BuildSkeleton` writes them from definitions and no build step ever writes one (`BlueprintSkeletonTests`), so the two halves never overlap. The access guard and startup's pool reservation read the same list. Only a blueprint holding a race can be deferred (`ResolvedBlueprint.Deferrable`), so shops, the chest and the test dummy are always built at spawn. It is built (`EnsureBuilt`) on `ProcessingTierEvents.TierChanging` into a simulated tier -- before any `TierChanged` handler -- and must be built by any other gameplay read or write that reaches it; it is never returned to a skeleton. Presentation never builds one: `MapViewQuery` draws/names it from its blueprint's appearance and seed, inspection shows `SpawnRecordRebuilder`' rebuild labelled "Unsimulated". In Debug, `SkeletonAccessGuard` (via `IEntityAccessGuard` on every other pool) throws when the simulation (`SystemManager.IsUpdating`) touches a pool a skeleton doesn't hold -- a missed build fails loudly instead of reading as "no loot". A build's spawn move goes through `SpawnMoves` -- usually next frame, since the tier drain runs after this frame's moves were read. Promotions wait for evicted neighborhoods' built creatures to be destroyed (`ProcessingTierResolver.PromotionsHeld` = `NeighborhoodStreamer.IsEvictingBuiltCreatures`, which runs evictions' built creatures ahead of other work), so builds reuse their storage.

## Presentation
- `PresentationBootstrapper`: fixed service set (FontService, SpriteBatchRenderer, LabelRenderer, TileRenderer, WindowService) — no module system (set is static).
- UI: `Window`/`WindowService`/`MapWindow`, content panes (`InspectionWindowContent`, `DebugWindowContent`). `NotificationCenter` can block gameplay update for a frame (checked in `GameLoop.Update` before `EcsContext` advances).
- **Presentation never touches the store.** It reads through `GameSession.Views` and writes through `GameSession.Commands`; no Presentation type may name `ComponentManager`, `EntityManager` or a component pool (component values are fine -- views hand them back). `PresentationStoreAccessArchitectureTests` scans the whole assembly; the only exemptions are `MapTintGrid`, `InspectionWindowContent` and `DiagnosticsWindow`. Pure arithmetic that reads no pool (shop price bands, scroll scaling, `InventoryQueries.TryResolveEffectiveItem`) is called directly. A game rule a UI gesture triggers reaches Game as a command call or an event (`AchievementNotificationDismissedEvent` -> `AchievementModule`), and the rule lives in its module.
- Shell composition: `ShellServices` (layers, `MapViewState`, camera, context menu, tooltip, `PointerState`, cursor text) goes only to composition points (`ElementFactoryRegistry`, `ItemWindowCoordinator`); an element takes the specific services it uses. `PointerState` is what `UiInputController` publishes at the end of each update for content drawn at the cursor. `ItemWindowCoordinator` builds the inventory/loot/shop/trade/Item Details/comparison/loot-box-results controllers and owns the rules between them (loot and shop mutually exclusive, trade follows shop, item clicks go to comparison when armed, `ReleaseEntity` on destroy). The item windows, grid and currency row share one `InventoryServices` record. Admin Mode's commands are `Game.Admin.AdminTools`, offered through `AdminContextMenuOptions`.
- Core design principles: remove ambiguity, remove unexpected actions. When an interaction could mean more than one thing (e.g. a drag with no single underlying identity to act on), don't guess — either resolve it to something concrete first, or refuse it outright with clear feedback (a disabled cursor, a no-op) rather than doing something the player didn't ask for.

## Scale
`GameLoop.InitialEntityCapacity` sized for TestMapBuilder's default 3072×3072×3 map, a 3×3 of 1024² neighborhoods (~660k entities; terrain and walls are flyweight cells in `Map`, not entities — see `Game/Terrain`) — not an arbitrary default; it sizes Direct pools. Packed/Multi pools index entities through pages (`EntityPages`, 1024 ids per page, allocated on first write), so a rare pool costs only the id ranges its holders fall in, and their dense storage starts at `InitialComponentCapacity` (small) or a registration's own `initialCapacity` and grows ×1.5 (`DenseCapacityGrowth`). `WorldSessionBootstrapper` also reserves the window's settled population before the first frame: (9 + cache 3) / 9 of the startup one, plus 10%, for what every creature holds (skeleton components), and 3 built neighborhoods' worth (x3.3 of the startup built population) for everything else -- without it, each early window shift resized the largest pools mid-drain (one 30-60 ms frame each). Population speed across a shift is bounded by gen-1 GC pauses, which track what each creature allocates and keeps: share immutable definitions (overrides, loot) instead of building one per creature.
