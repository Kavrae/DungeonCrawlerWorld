# CLAUDE.md

Guidance for Claude Code in this repo.

## Git
Local, read-only inspection/comparison commands (`git status`, `git diff`, `git log`, and similar) are allowed. Do not run anything that writes to the repo or touches a remote — `add`, `commit`, `push`, `fetch`, `pull`, `stash`, `reset`, `checkout`/`restore`, branch/tag creation or deletion, etc. Leave those to the user.

## Commands
```
dotnet build DungeonCrawlerWorld.sln
dotnet test Tests/Tests.csproj
dotnet test Tests/Tests.csproj --filter "FullyQualifiedName~ClassName.MethodName"
dotnet test Tests/Tests.csproj --filter "TestCategory=Performance"
dotnet run --project DungeonCrawlerWorld/DungeonCrawlerWorld.csproj
```
- net10.0, Nullable enabled, LangVersion latest, all projects. Nullable warnings are build errors (root `Directory.Build.props`): a non-nullable type is the guarantee a dependency is present, so internal code takes it as non-nullable with no runtime null guard. Guards (`ArgumentNullException`) stay only at the mod-facing boundary -- public entry points a mod calls directly -- and in post-construction `Wire` methods.
- Tests: MSTest (`Microsoft.VisualStudio.TestTools.UnitTesting` global using). `TestCategory=Performance` tests (wall-clock ratio checks) are excluded from an unfiltered run by Tests.csproj's default `VSTestTestCaseFilter` — pass any `--filter` and that default is replaced, not ANDed.
- DungeonCrawlerWorld.csproj auto-runs `dotnet tool restore` (mgcb tools) before Restore.
- Benchmarks: `--seed=N` (deterministic world), `--benchmark-frames=START-END` (one-shot per-system report, frames START to END-1), `--headless` (simulation only, no window, exits when done), `--diagnostics=frame,memory,startup,leak` (or `all`; opt-in, off by default; reports land in `Log/diagnostics/`). Drive them through the `phase-performance-testing` skill, which also does before/after A/B runs.
- Tests.csproj refs Mods.ExampleMod/Mods.TestFixtures with `ReferenceOutputAssembly="false"` — built to disk, loaded at runtime via ModuleLoader (real mod pipeline), not compiled against.

## Layers (one-way deps)
`Engine → Game → Presentation → DungeonCrawlerWorld(exe)`
- **Engine**: generic ECS + modding infra. No game-specific knowledge.
- **Game**: world/map, blueprints (entity templates), built-in modules (Core, Movement, Health, Energy, Race, Class).
- **Presentation**: FNA (XNA-compat) rendering + window/UI. No gameplay logic.
- **DungeonCrawlerWorld**: exe. `GameLoop.cs` = composition root. `WorldSessionBootstrapper.cs` = the game session plus what only the app owns (`WorldSessionContext`: `GameSession`, player activity log, `AdminTools`, reserved entity ids). `ShellBootstrapper.cs` = construction and layout only -- no behaviour lambdas; rules between windows live in Presentation (e.g. `ItemWindowCoordinator`). `ElementFactoryRegistry.cs` = pooled element factories. `Presentation/Input/UiInputController.cs` = input.
- **Game → outside it**: `GameBootstrapper.Build` returns a `GameSession` (`Game.Bootstrap`), built by name from the build's `GameModuleContext`, which stays the modules' build-phase API and is never handed out. `Catalogs` (action, item, loot box, achievement, status-effect display, terrain, blueprint), `SimulationClock`, `Views` (`GameViews`: read-only, per-session views in `Game.Views` -- map, inventory, shop, currency, hotkey bindings, health, stat modifiers, ability scores, action state, transforms, naming, and `ActionSourceNaming` for the name shown for what caused an effect), `Commands` (`GameCommands`: per-session write services in their feature's namespace -- `InventoryCommands`, `CurrencyCommands`, `ShopCommands`, `HotkeyBindingCommands`, `LootboxCommands`, `LootCommands`, `PlayerCommands`), `Internals` (factory, skeletons, rebuilder, teleporter, tier resolver, roster, moved entities). A service holds its own pools, catalog, bus and player, so a caller passes only ids and values. Each wraps the feature's static `*Actions`/`*Queries`, which stay the implementation because systems call them with pools of their own. A new outside-of-Game read or write is a method on a view or command, not a new pool handed to Presentation.
- **Content**: copies `Content/Fonts/*.ttf` to output only; not a compiled MonoGame pipeline.
- **Mods.ExampleMod**: real mod pattern — refs Engine/Game with `Private="false"` (no duplicate copies shipped). **Mods.TestFixtures**: mod DLLs for ModuleLoader failure-path tests.

## ECS (Engine/ECS)
- `EcsContext` = EntityManager + ComponentManager + SystemManager + EventBus. Built by `EcsBuilder`'s stages, each a type that can only be advanced once and only in order: `EcsBuilder.Begin(modules, settings, ...)` (checks every module's `Requires`, sorts by `RunsAfter`/`RunsBefore` keeping the caller's order where unconstrained) → `SortedModules.RegisterComponents()` → `RegisteredComponents.Configure(context)` → `ConfiguredModules.RegisterBehavior()` → `RegisteredBehavior.Complete()`. Each phase runs for every module before the next: ALL components before any `Configure`, every `Configure` before ANY systems. Systems run in that order, and so do event subscriptions made in `RegisterBehavior` (e.g. Health's `StatModifierExpiredEvent` handler before AbilityScores').
- Pools: `RegisterDirectPool/RegisterPackedPool/RegisterMultiPool`, each with `MergeAction<T>`. Blueprints always `Merge` not `Add` (composable, no collision throw).
- Systems: `ISystem` + `StripeCount`. `SystemManager` runs every system every frame; each processes only `Count/StripeCount` of its pop per call (entity striping, flat per-frame cost vs periodic-system spikes). `EntityStripeSet` buckets by `entityId % StripeCount`, updated incrementally via EntityAdded/EntityRemoved (no rescan).
- Tiered systems: `TieredEntityStripeSet` = one `EntityStripeSet` per processing tier (Local/Neighborhood/Borough/Beyond), bucket stripe count = base `StripeCount` × tier divisor (`ProcessingTierDivisors`, `ushort` — `byte` silently truncated before). A tiered system implements `ITieredSystem`: expose `Tiers`, per-entity work in `UpdateBucket(time, entityIds, framesPerVisit)`, per-frame work in `BeginFrame`, and `Update` must be exactly `=> TieredSystemRunner.Run(this, time)`. `SystemManager` owns the tier loop and never calls a tiered system's `Update` — anything else put in `Update` is silently skipped. `SystemManager.SimulatedTierCount` = which tiers run at all (game-injected policy; P2 hook).
- Entity ids are recycled the moment an entity is destroyed. Anything that refers to another entity beyond the current frame holds its `EntityKey` (`EntityManager.Keys`, issued once, never reused), not its id. Modules take the key table from `GameModuleContext.EntityKeys` (the EntityManager's own) and pass it to `ActionSource.FromEntity`. Holders: `ActionSource` (8 bytes: kind, key, and an `EntityIdentities` handle for the name and crawler number it had) and `DeadComponent.KilledBy`. Compare a source with the player through `IPlayerQuery.PlayerEntityKey`/`source.IsEntity`, and display it through `source.Identity`. `EntityManager.EntityDestroying` fires before components are removed: `GameBuildPass` clears aura sources, map footprint and tier membership there, `ShellBootstrapper` clears UI selections (the inspected entity, and `ItemWindowCoordinator.ReleaseEntity` for item windows) -- state kept outside the pools about an entity must let go there too. `EntityManager.IsDestroying(id)` is true from `EntityDestroying` until the components are gone, for a handler that must tell a removal that is part of destroying the entity from one that isn't. `MultiComponentPool.ComponentRemoving` fires before every removal of an instance (not `Clear`), with it still readable; a handler must not add to or remove from that pool. `SystemManager.RegisterFirst` runs a system before everything registered so far.
- **Scale every time-based field by `framesPerVisit`, never a constant.** A coarse-tier entity is visited every `StripeCount × divisor` frames, so a value advanced by 1 (or by base `StripeCount`) per visit moves at a fraction of real time. This defect recurred across ~6 systems before the loop moved into `SystemManager`. It no longer applies to timers at all — those are deadlines now (see the Timers bullet), which is what made the whole class of bug go away; it still applies to anything else a tiered system accumulates per visit, e.g. `ComplexHealthRegenSystem`'s regen amount.
- Timers: **nothing decrements a countdown any more.** Store `FrameDeadline.After(now, frames)` as a `uint` frame and compare against `EngineTime.FrameCount` (in systems) or `SimulationClock.CurrentFrame` (elsewhere; `GameModuleContext.SimulationClock`, advanced by `SystemManager.Update`). Two shapes, by what reaching the deadline means:
  - **Something happens** (a damage tick, an expiry, a windup resolving) → the component implements `IScheduledTimer` (or `IKeyedScheduledTimer` for a Multi pool, keyed by a stable instance id) and its owning system drives a `PackedTimerWheel`/`MultiTimerWheel`. Scheduling is automatic: the wheel observes the pool's `ComponentChanged`, so any normal write of `NextTickFrame` schedules it and no caller has to remember. Re-arm a periodic timer with `timer.RepeatEvery(period)` on the `ref` a pool updater hands you (`ScheduledTimerExtensions`) -- it counts from the deadline that fired, so the cadence stays exact if a firing was ever late, and there is no `now` to pass wrongly. `FrameDeadline.Never` parks a timer (permanent modifiers/immunities are never scheduled).
  - **Nothing happens, it just stops gating** (action lock, movement backoff, regen lockout) → a plain `uint` field and a comparison at the reader. No system, no wheel, no per-entity cost at all.
  - Anything that writes a timer takes `now` as a required parameter rather than reading an ambient clock, so a test can't silently disagree with the frame the system is running on.
- Choosing a shape: no per-entity population (event queues) → plain `ISystem`, no stripe set. Must react the frame something was queued (player input, deaths, dodge windows) → plain `EntityStripeSet`, don't tier. Otherwise → `ITieredSystem`. Event-driven (`ProcessingTierSystem`), or driven by the frame's moves and a timer wheel (`AuraSystem`, `TerrainContactSystem`) → plain `ISystem` running its own loops.
- Tiers are decided by `ProcessingTierResolver` (Game), event-driven by `ProcessingTierSystem` — no periodic scan. Local = Chebyshev radius 80 on the player's layer; otherwise the entity's 1024² neighborhood (`Game.World.Neighborhoods`, shift/mask, floors negatives) decides: the window centre's = Neighborhood, the 8 around it = Borough (frozen, `SimulatedTierCount = 2`), further = Beyond. The centre (`ProcessingTierResolver.WindowCenter`) follows the player's neighborhood once they are 64 tiles past its edge (`WindowShifted`). Every positioned entity is tiered, not just movers. Entities are born tiered: `ProcessingTierResolver.CreateEntityAt` writes the tier as the first component, before the blueprint adds pooled components (stripe sets read it in `OnMemberAdded`); `World.EntityPlaced` → `EnsureTiered` is the catch-all for other placements. An untiered entity fails open to Beyond in every stripe set. Player pinned Local once at spawn.

## Modding (Engine.Modules)
- `IModule` = identity `Guid Id` + three lists of other modules' Ids + the phases that need no context: `DeclareSettings` (default no-op) and `RegisterComponents(ComponentRegistration)`. `IModule<TContext>` adds `Configure(TContext)` (default no-op) and `RegisterBehavior(BehaviorRegistration<TContext>)`, which carries the same context -- so a module keeps no fields between phases, and `Configure` only fills what another module's `RegisterBehavior` reads (catalogs, registries). `RegisterBehavior` wires everything a module runs -- systems, event handlers, and setup that decides which systems exist (Achievements' triggers decide whether `AchievementPollingSystem` is registered) -- after every `Configure`, so no catalog is still filling; never subscribe or read another module's catalog in `Configure`. `IGameModule` = `IModule<GameModuleContext>`. `Requires` (must be present -- presence only, no order), `RunsAfter`/`RunsBefore` (system order only; an absent target is ignored). Requiring never implies order: every component registers before any `Configure` or system, so another module's pool is there whatever the order. A built-in declares `public static readonly Guid ModuleId` and `Id => ModuleId`; dependents name it as `HealthModule.ModuleId`, so a mod replacing it by Id still satisfies them. Mutual `Requires` is fine; a `RunsAfter`/`RunsBefore` cycle throws naming every link and the module and list that declared it (e.g. "Movement runs after Core (Core.RunsBefore)").
- Settings (Engine.Settings): a module declares typed `SettingKey<T>`s (owned by its `Id`, so a replacement takes them over) in `DeclareSettings`; `SettingsCatalog.Declare(modules).Resolve(sources)` gives frozen `SettingValues` plus a `SettingsFailure` per rejected override (unknown key, bad value, malformed entry). Every setting is startup-scoped and readable in every phase; `CommandLineSettingsSource` reads `--setting=ModuleName.SettingName=Value`. Settings may size and tune pools but never decide whether a built-in pool exists. No module declares one yet.
- Gameplay tags (Engine.Tags): a `GameplayTag` is a dot-separated name (`Damage.Fire`) whose parent is the name minus its last segment; `GameplayTagSet` (immutable, built once per definition, never per frame) answers `Has` parent-aware and `HasExact` not; `GameplayTagQuery` (all/any/none) is a shared instance on definitions. Modules declare tags in `DeclareTags` (built-ins: `Game/Tags/GameTags.cs`, declared by Core); `ContentTagValidation` fails a build whose actions/items use an undeclared tag. Tag ids vary between runs -- never order, save or persist by id. **Combine, don't nest:** a tag has a parent only if every child always is it; a property that applies to unrelated things is top-level and combined (`Magic` + `Damage.Fire`, never `Damage.Magic.Fire`). An activator's classification comes from `IActionActivator.ImpliedTags` (Spell → `Action.Spell` + `Magic`), never hand-listed.
- `ModuleLoader.LoadFromDirectory<TContext>`: reflects `*.dll` into collectible `AssemblyLoadContext`s and returns a `ModuleFactory<TContext>` per public concrete `IModule<TContext>` (each constructed once while loading, so a type that won't construct is reported then). Per-DLL/type failures caught → `ModuleFailure`, never aborts whole load.
- `ModuleSet.Combine`: merges built-ins + mods, replaces built-in by `Id` match. A replacement takes the replaced module's place in the order and must keep its contract: it registers every component type the built-in did, as the same pool kind (more is fine, and it may register no systems). Partial replacement is a TODO.
- Every build is a self-contained `Game.Bootstrap.GameBuildPass.Run`: fresh module instances from factories, its own World over its own Map, EventBus, key table, MathUtility and context -- nothing one build creates is reachable from another, and none depends on running before or after another. After `RegisterComponents` it builds the World and the `GameModuleContext` from the registered pools, so every context member (resolver, simulation scope, floating-text feed, entity factory) is complete from construction -- no `Wire`/late setter anywhere. That makes every build need `GameModuleContext.FoundationModuleIds` (Core, ProcessingTier, Blueprints), checked with a named error. After `RegisterBehavior`: `SpawnMoves` first, skeleton access guard, destruction handlers, the simulation-resume subscription, the clock, the `LocalTierRoster`. `GameBuildPass.BuildModules` is the module build alone, for a test of a few modules.
- `ModValidation.Validate(modsDirectory, settingsSources)` → `ValidatedMods`: loads mods, checks the replacement contract, and trial-builds each (with the built-ins only) in its own pass over `GameBuildPass.CreatePlaceholderMap()`; drop on throw. The game-start / mods-changed step. `GameBootstrapper.Build(validatedMods, map, ...)` = the new-game / load step: the session's pass over `map` plus the `SpawnRecordRebuilder` staging pass, returning a `GameSession`. `BuiltInModules()` lists the built-ins as factories. Load and settings failures only reach `Console.Error` today.
- Built-in pools are always there in a game (mods can only add or replace modules, and a replacement keeps the components), so code always fetches another built-in's pool with `Get*Pool` -- never `IsRegistered` or a nullable pool. A module that fetches another module's pool in `RegisterBehavior` declares it in `Requires`; `BuiltInModulesTests.EveryBuiltInModule_BuildsWithOnlyWhatItRequires` fails otherwise. `BuiltInModulesTests` also pins every system's run order -- a change to it should be deliberate.
- Dependencies point from a feature to what it builds on, never back. A status effect acts on health only through Health's API (`HealthDamage`, `HealthHeal`, `BodyPartDamageEffects` -- e.g. Burning locks a burning part out of regen with `ResetRegenLockout`), and Health never reads a status effect's components; Poison is the model.
- The build checks content after every `Configure`: `AuraContentRegistration` registers every aura definition the content names (see Auras below) and `ContentTagValidation` fails a build that uses an undeclared tag. Both reach effects through `EffectContent.ForEachEntry` -- every entry of every action, item, terrain contact and aura, nested ones included -- and ask each entry what it names (`IEffectEntry.ReferencedTags`/`ReferencedAuras`/`NestedEffects`); a new entry that names content implements those rather than being added to a check, and a new kind of effect holder is added to `EffectContent` once. A module whose content grants another module's status effect `Requires` it (`TerrainModule` → `BurningModule`). A namespace must not share a name with a type other modules use -- `Game.Modules.X` hides type `X` from every `Game.Modules.*` namespace -- hence `TerrainContacts`.
- Tests: `BuiltInTestComponents.RegisterAll` (every built-in pool on a bare `ComponentManager`), `BuiltInTestModules.Build(map)` (the whole built-in module set as one `GameBuildPass`), `BuiltInTestModules.BuildModules(modules)` (a few modules alone, foundation modules added), `TestWorlds.Create`/`Over` (a World without the modules), `TestModuleRegistration` (one module's `RegisterComponents` on a bare `ComponentManager`, default settings), `EmptyPools` (stand-ins for pools a test doesn't exercise), and `TestSystems`/`TestHealth`/`TestActionEffects` (the old optional signatures, filling in `EmptyPools`).

## Auras and terrain contact (Game.Modules.Auras, Game.Terrain)
- An aura is an `AuraDefinition` (Guid, name, glow colour, `Effects` -- the same `Effect` lists an action or item holds -- `Tags`, `Magnitude`) that **lives with whatever radiates it -- there are no standalone aura classes and no module registers one**: `BuiltInTerrain.LavaAura` (a `StatusEffectGrant` of Burning with `TopUpTo`, on a random body part), `BuiltInTerrain.HolyGroundAura` and `HealingShrine.Aura` (`DirectHeal`, flat 1 per point of power, to the part healing priority picks), `ToxicIdol.Aura` and `ToxicAuraAction.Aura` (Poison, `TopUpTo`; two auras, so they don't add), `ScrollOfTorch.Aura` (no effects, glow only). A source holds the definition itself (`TerrainAura`, `AuraGrant`, `AuraSourceGrant`). `GameModuleContext.Auras` (`AuraCatalog`, session-local `byte` ids -- never persist one; at most 256 in a session) is filled by the build from the content (`AuraContentRegistration`), and `AuraCatalog.Register` turns a definition into an id at any time, free when it is already known -- so an aura made at runtime needs nothing registered first. The Guid is what makes two sources the same aura (their powers add): two things that should add share one definition, two that shouldn't have their own. Two different definitions in the build's content sharing a Guid fail the build (`AuraContentRegistration`): each re-registers its definition when it radiates, so they would take turns replacing each other, each turn a world-wide rescan. Effects apply with no source entity (no Outgoing modifiers, no ability bonus, no crit), credited to the strongest single contributor at the cell (see Attribution below), scaled by the power at the entity (`AuraMagnitude.Power`) or not at all (`Flat`). Glow colour belongs to the aura, never the source. Nothing keeps a copy of a definition: effects and colour are read from the catalog by id each time, so re-registering a Guid (`AuraCatalog.DefinitionChanged`) takes effect on the next tick, and the same holds for a terrain's aura (`TerrainRegistry.DefinitionChanged`).
- A source is `(aura, power, size)`: `AuraSourceComponent` on an entity (Multi pool: at most one source of an aura with no key, plus one per toggle holding it, keyed by `HeldGrantKey`), `TerrainDefinition.Aura` (`TerrainAura`), `BlueprintDefinition.Auras` (`AuraGrant`), or `AuraSourceGrant` on an action. Size is its reach in tiles of Manhattan distance; the aura's `Falloff` (`AuraFalloff`, Engine.Math) gives the value at each distance: `Linear` from power at the source to about power / (size + 1) at the edge, rounded up, or `None`, full power to the edge. Overlapping sources of one aura add. The field fixes an aura's falloff while it holds any source of it, so a replaced falloff takes effect once they have gone. A `None` move writes only the cells that changed sides; a `Linear` one rewrites both diamonds.
- **An aura's effect is applied only by an exposure's tick**, once a second (`AuraEffects.TickIntervalFrames`), never on entering range. Coming into range starts an `AuraExposureComponent` whose first tick is staggered within the next second; a tick that finds the entity out of range ends it and applies nothing. The power is the cell's total for that aura minus the entity's own sources' power. Anything in range that isn't dead holds an exposure, whether or not the effects can do anything to it -- never cache "this entity can't be affected"; a tick that lands nothing is cheap, and a refused one is reported once per stay (`AuraExposureComponent.Refused`).
- `AuraField` (`GameModuleContext.AuraField`) is the one structure holding where auras reach: totals per (cell, aura), a coverage bit per cell (`AnyAuraReaches` -- test it before asking per aura), `Version`, and the glow (`TryGetGlow`: aura colours weighted by power), which `GameViews.AuraGlow` hands to `MapWindow`. It follows terrain itself (`TerrainChangedEvent`/`TerrainLoadedEvent`/`TerrainUnloadingEvent`); `AuraSystem` puts entity sources in.
- Entity sources: adds are observed (`AuraSystem` watches the source pool, so a blueprint or anything else may add one directly), removals are announced (`AuraSourceRemovedEvent` -- always remove through `AuraSourceEffects`/`AuraSources`), and a source is never changed in place. First placement is immediate at any tier; a Local source resyncs on its move; any other tier is queued and resynced a few a frame. Each source is scanned by its own reach (`AuraField.ReachOf`), and a move scans only the cells that changed sides between its old and new diamond; the whole diamond is scanned on add, remove, first placement, or when the last placement exposed nobody. Nothing unsimulated gains an exposure; `SimulationScope.EntityResumed` exposes it when it resumes.
- Attribution is credit only (the effect still has no source entity): `AuraField.PowerReaching(..., out credit)` names the strongest single contributor at the cell -- an entity source's entity (`AuraSystem.AttributionOf`: an anchor's placer, else `FromEntity`), else the terrain's share (the total minus the entity sources'), else the aura itself when several terrain types radiate it (`ActionSource.FromAura`). An entity source wins a tie with terrain; entities tie to the lowest key. Kill credit follows it. Entity sources are indexed by 32x32 chunk (`AuraSourceIndex`, inside `AuraField` -- write through `AddEntitySource`/`MoveEntitySource`/`RemoveEntitySource`), attribution fixed at first placement.
- **Only sources an entity carries leave it alone.** A placed aura reaches its placer like anyone else; an aura that shouldn't hit whoever placed or holds it grants them an immunity first (Toxic Aura holds a Poison immunity under its toggle's key) -- never add a placer exclusion.
- Anchors: an aura placed on a tile is an ordinary entity (`AuraAnchor` blueprint, `AuraAnchorComponent(PlacedBy, OwnerKey, HeldGrantKey)`, non-blocking, `NonBlockingKind.None` so Target mode never marks one) carrying the source, spawned by `AuraAnchors` (in `EffectServices`). It ends with its last source (destroyed by `AuraAnchorEndingSystem` the next frame, never inside the removal), with its owner's destruction, or when its neighborhood unloads; ending one asks the toggle holding it to switch off, so a toggle is never on with nothing behind it.
- Terrain contact: `TerrainDefinition.Contact` (`TerrainContact`: a list of `Effect` -- the same lists an action or item holds, see Effects below -- plus `Tags`, optional `RepeatEveryFrames`, `GroundContactBodyPart`) applied by `TerrainContactSystem` on stepping on and at the repeat while the entity stays, with no source entity and attributed to the terrain. `GroundContactBodyPart` (bottommost part as fallback) reaches only the entries that ask for it with `BodyPartTargeting.GroundContact`: lava's damage and burn land on the feet, Holy Ground's blessing asks for nothing and is the whole entity's. **A buff or protection that holds while an entity is in an area is a contact with a repeat** and a `StatModifierGrant` with `Stacking: RefreshFromSameSource` (Holy Ground), not a new mechanism. Terrain changing under an entity is stepping onto the new terrain (`TerrainChangedEvent`; `TerrainRegistry.DefinitionChanged` for a terrain that gains a contact), and every repeat reads the terrain where the entity stands -- never add a second way to change a cell's terrain that announces nothing.
- Effects (`Game.Effects`): one vocabulary for everything that applies effects. An `Effect` is a list of `IEffectEntry` (general ones in `Game/Effects/Entries`, feature-owned ones beside their feature: `AuraSourceGrant` in Auras, `DodgeActivation`/`HotkeyExpansionGrant` in Actions); an applier builds an `EffectContext` (struct, passed `in`) over the build's one `EffectServices` (`GameModuleContext.EffectServices`; a module that reads it lists `EffectServices.RequiredModuleIds` in `Requires`) and calls `EffectSequence.Apply`. **No applier lists entry types and no entry knows what applied it.** The context says who caused it (`Source`, an `ActionSource`), whether a live entity's stats shape it (`SourceEntityId`, null for terrain and auras: no ability bonus, no Outgoing modifiers, no crit), `Magnitude` (scales amounts -- damage, healing, mana, stacks -- never durations), `GroundContactBodyPartRule` and `AnnouncesRefusal`. **Which body part an effect lands on is the entry's own statement** (`BodyPartTargeting` on `DirectDamage`, `DirectHeal`, `StatusEffectGrant`: `Unspecified`, `GroundContact`, `Random`, `Of(type)`), resolved at each application and handed to the applier (`IStatusEffectApplier.ApplyStacks(..., bodyPartId)`); nothing infers it from what applied the effect or from what else the target stands in -- a contact never changes what an aura does. The lava aura burns a `Random` part each tick, so parts add up; an effect that can't be held per part (only Burning can today) and a target without body parts hold it on the entity. `Apply` returns an `EffectOutcome` (`NoEffect`/`Refused`/`Applied`) so something that applies repeatedly reports a refusal once per stay (the `Refused` bit on its exposure). Stacks go through `IStatusEffectApplier.ApplyStacks` -- one immunity check and one write however many are asked for -- never a per-stack loop.
- **Every amount an entry carries goes through stat modifiers on both ends**, through `EffectModifiers.Scale` (Outgoing on `SourceEntityId` when there is one, then Incoming on the target unless `EffectContext.NoTargetEntity`; both conditional on `ActivatorTags`): damage (Outgoing here, Incoming at `HealthDamage`, which DoTs share), healing (both at `HealthHeal`, which regeneration shares), durations, mana restored and drained, status stacks, proc chance, aura power and size. Modifiers are read live, at application -- a Delayed activation's are the ones in effect when its windup ends; nothing snapshots them. An entry declares its pairs in `IEffectEntry.AmountModifiers` (none for one with no amount); a new entry with an amount scales it through `EffectModifiers` and declares the pair. New `StatModifierTarget` members are appended, never inserted. **Health and mana amounts are never rounded** -- damage, healing, mana drained and restored, costs included: both are held as floats, so a modifier can't round a cost down to free or a hit down to nothing (a halved 1-mana upkeep takes 0.5). Only an amount that must be whole -- stacks, durations in frames, aura power and size -- rounds to the nearest (`EffectModifiers.ScaleToUShort`/`ScaleToByte`), never truncates; display rounds only where it is drawn (floating damage text: nearest, at least 1).
- **A cost is an activation effect.** Every action and item has `ActivatableDefinition.ActivationEffects` (an `init` property, empty by default): what using it applies to its user -- source and target both -- before anything else it does: a cost (`ManaDrain`, `HealthDrain`) or anything else (stunning the caster in place). There is no cost field anywhere; a spell's mana is a `ManaDrain` among its activation effects. They are asked first and all or nothing, through `ActivationEffectsApplier`: `EffectSequence.CanApply` asks a list against one `EffectReservations`, so two costs are checked together. They are taken when a use goes ahead -- Immediate and FreeCast at activation, Delayed when its windup starts, never refunded -- and turning a toggle off is not a use. A refusal is an `EffectRefusal` with an `ActivationBlocker` of its own (`ActivationQueries.BlockerFor`) and text of its own (`ActivationBlockerText`): a new way to refuse adds a member to both. An entry that takes a resource implements `IResourceDrain`, which is how `ActivationCosts` (per-resource totals: the hotbar badge) and `ManaUse.DrainsUsersMana` (whether a grant gives the entity a mana pool, read from the definition it will use) find costs without listing entry types. A health cost (`HealthDrain`, through Health's `HealthCost`) is refused rather than killing its payer, split evenly across a body plan's parts, and never reduced by damage reduction.
- **Where an entry lands is its own statement** (`IEffectEntry.Placement`): `OnEachTarget` (default: every entity the resolved tiles reach), `OncePerActivation` (once, on the marked entity if there is one, otherwise at the centre tile -- `AuraSourceGrant`, so Target mode lights an entity and Ground anchors the light), `AtLocation` (once at the centre tile, whatever is marked; nothing uses it yet). An activation applies through `EffectSequence.ApplyOnEachTarget`/`ApplyOnce`; `Apply` is for everything applied to one entity (an aura tick, a contact, a chained effect, where a once-placed nested entry is applied per target, as the chain is). The centre is `EffectContext.TargetLocation`: the aimed tile, or the caster's for Self.

## Targeting (Game.Modules.Actions)
- **Game resolves targets, not Presentation.** An activation request and `PendingWindupComponent` carry a `TargetSelection` (mode, aimed tile, the marked entity's key and which footprint tile was aimed at, effective range and area after scroll scaling -- `ScrollScalingEffects`, in Game), never tiles. One function, `TargetResolution.Resolve` (`GameModuleContext.TargetResolution`; Presentation through `GameViews.TargetingView`), turns it into tiles: at activation for Immediate and FreeCast, at the windup's end for Delayed, every frame for the preview and the windup telegraph, and for NPCs -- so what is drawn is what lands. Never resolve a shape anywhere else.
- Two modes (`TargetingMode`): **Target** marks the entity on the confirmed tile (Blocking, else a Tiny one picked from seeded rolls, else a Phasing one; nothing there resolves as Ground), and a Delayed activation follows it -- centred on its tile when the windup ends, clamped to the farthest tile in range toward it; destroyed, it lands on the marked tile; dead, on the corpse. A large entity keeps the aimed footprint tile. **Ground** is the aimed tiles and whoever stands on them when it resolves. Immediate and FreeCast land the same either way.
- What has a mode is the spec's (`TargetingSpec.Modes`: `Both` or `GroundOnly`) and so is what Target affects (`TargetModeAffects`: `Area` -- the shape around the target -- or `MarkedOnly`, potions). Melee, Adjacent shapes and Dodge are `GroundOnly`; `TargetingContentValidation` fails a build that gives them `Both`.
- The mode is the player's, held in Presentation (`MapViewState.TargetingMode`, default Target, session only), switched by Left Alt (`TargetingModeSwitch`) with the new mode shown at the cursor, and refused mid-windup with a cursor message rather than ignored. A toggle action switched on in Ground mode places what it places on the holder's tile (`Toggles.TurnOn(..., placesAtHolderTile)`).
- Spawn order decides entity ids, and a pool pages by id (1024 per page): spawn entities that hold the same rare components together. `TestMapBuilder` plans a neighborhood's shrines first, in batches -- interleaved with creatures they cost 31 MB of pools and 18% of the aura system.

## Toggles and windups (Game.Modules.Actions)
- A toggle is any action or item with `ActivatableDefinition.Toggle` (`ToggleSpec`): its own `Effects` are what it **holds** while on, the definition's `ActivationEffects` -- as for any action or item -- what turning it on **takes**, `Periodic` (`TogglePeriodicEffects`) what it does every interval while on. All three apply with source and target its holder. No separate cost type: a cost or upkeep is an effect (`ManaDrain`). An item is a toggle exactly when its activator is `ToggleItemActivator`; a toggle action must be Self-targeted; a toggle may hold a grant with no end (`IEffectEntry.GrantsUntilRevoked`) only if it is an `IReversibleEffectEntry` -- a permanent `StatusEffectImmunityGrant` can (held under the toggle's key), a permanent `StatModifierGrant` can't yet, which is what stances wait on. `ToggleContentValidation` fails a build that breaks any of these.
- **A toggle's held effects are applied and taken back only through `Toggles`** (`GameModuleContext.Toggles`): `TurnOn` adds an `ActiveToggleComponent` (Multi pool, one per toggle that is on, its own `Key`, its `Owner` the action or item stack) and applies the held effects with `EffectContext.HeldGrantKey` = that key; `TurnOff` reverts them under the key. So any number of toggles with the same effect stack and each ends only its own (keyed aura sources). Neither applies activation effects, checks a lock or flips an item: the caller has. `DeathSystem` removes only unkeyed aura sources: what a toggle holds is the toggle's to end.
- Periodic effects are **asked before they are applied** (`IEffectEntry.CanApply`, `EffectSequence.CanApply`) and are all or nothing, as activation effects are (see Effects). A turn-on whose activation effects can't apply is blocked by the refusal's own blocker (`ActivationQueries.GetBlocker`); turning off takes nothing and is never blocked.
- Each feature that owns toggles registers an `IToggleOwner` (resolve the definition, switch off, whether it ends with its holder): Actions (`ActionToggleOwner` -- the component is the whole on/off state; ends at death) and Inventory (`ToggleItemHolderSync` -- ends at death only with periodic effects). `ToggleUpkeepSystem` (plain `ISystem`, a `MultiTimerWheel` over the toggles) applies periodic effects every interval, the first one interval after turning on, and asks the owner to switch off a toggle whose upkeep can't be met or whose holder died (`ToggleEndedEvent`). A holder that isn't simulated, or isn't on the map (a trade-offer entity), isn't ticked and owes nothing for that time.
- **An item's lit state is the unit's** (`ToggleItemActivator.IsToggledOn` in the stack's `Override`) and travels with it; it changes only by moving a unit between the lit and unlit stacks (`ToggleItemActions.TryToggle`). `ToggleItemHolderSync` observes the stack pool (`ComponentChanged`/`ComponentRemoving`) and keeps the holder's active toggles equal to its lit units, so every transfer, merge or destroy path is covered with no caller remembering. Any holder can hold a lit item, alive or dead, on the map or not. A lit stack never joins a Merged Stack cell.
- **Which hotkey slot follows a unit that changes stack** (a toggle flipped, a wand's charge spent) is decided, never guessed: the activation carries the pressed slot (`PendingItemActivationComponent.ActivatedFromSlot`), and `ItemHotkeyBindingActions.RepointAfterUnitMoved` moves that slot, plus every slot still on a stack that is now gone.
- **An action or an item stack is named by one value, `ActivatableReference`** (`ActivatableKind` Action by action id, Item by stack instance id): what a windup resolves into and what a toggle belongs to. A view turns one into its definition only through `ActivatableLookup` (Game.Views) -- the entity's effective action (its override, through `EntityActions`), never the bare catalog entry, or the stack's effective item. Inside Game, each kind is resolved by the feature that owns it (`DelayedActionSystem` and `WindupResolvers` for windups, `IToggleOwner` registered by kind for toggles).
- Timing, actions and items alike: FreeCast flips at once whatever the lock; Immediate needs the lock clear and sets it; Delayed, turning on, winds up and goes on when the windup resolves -- turning off is at once. Activation effects (a spell's mana among them) are charged when the windup starts and not refunded if it is cancelled. **One windup component for actions and items**: `PendingWindupComponent` (its `Activatable`: action or item stack), started by `Windups.Begin` (sets the lock, copies its deadline); `DelayedActionSystem` resolves an action's, and hands an item's to the resolver Inventory registers (`WindupResolvers`, `ToggleItemWindupResolver`). Every windup rule -- one per entity, cancel, Stagger, Dodge's release, freeze, the charge-fill telegraph -- covers both. A windup that ends early (cancelled, holder dead, stack gone) turns nothing on.
- Presentation: a toggle is never armed -- a hotbar press, Activate or double-click queues it at once on the player's tile, and no window closes. "On" is one marker (`ToggleActiveMarker`) on a lit cell, a lit item's slot and a toggled-on action's slot; "Active" and the turn-on/upkeep lines come from `ToggleText` in every tooltip and Item Details.

## Diagnostics (Engine.Diagnostics)
- **Emit, never thread.** Measured code reads a static `EngineHooks` channel -- `FrameCosts`, `SimulationFrames`, `Sessions`, `DiagnosticScopes` -- and does nothing else when its `Listener` is null. Never pass a recorder, profiler or `DiagnosticsEngine` into the code it measures. Each channel holds one listener (subscribing a second throws); `DiagnosticsEngine.Start()` subscribes whatever its features need (`GameLoop`'s constructor, `HeadlessBenchmark`) and fans out internally, `Dispose` unsubscribes. Channels are process-wide: a test that subscribes is `[DoNotParallelize]`.
- `SystemManager.Update` is the one frame boundary (`SimulationFrames`); a host calls only `EcsContext.Update`. The benchmark window, the "GameLoop" / "EcsContext.Update (all systems)" row, startup stability, memory/leak sampling and the 5 s `latest.json` report all run from it, so they pause with the simulation. Keep benchmark row names stable -- the benchmark skill and saved results read them.
- `EcsContext.BeginSession()` marks the build a host simulates (the last step of `WorldSessionBootstrapper`); disposing it -- through `WorldSessionContext` -- ends it. Trial and staging builds never begin one. Memory and LeakDetection trackers are per session.
- A frame cost at a site that runs a few times a frame is `using (EngineHooks.FrameCost(category, group, item))`. A per-system or per-event path (`SystemManager.Update`, `EventBus.Publish`) branches on `EngineHooks.FrameCosts.Listener` itself instead, so with nothing listening it runs as a bare call -- no try/finally, no arguments evaluated.
- A startup step or build phase worth timing is `using (EngineHooks.DiagnosticScope("Name", detail))`: a constant name, and a detail the caller already holds (a module's `Name`), never a string built for it. `EcsBuilder`'s stages and each module's phase emit them; `StartupProfiler` records them nested until the first simulation frame.
- A value worth watching over time is a gauge: `EcsContext.Gauges.Register(group, name, kind, read)` while building the session (frozen at `BeginSession`, cleared on dispose), registered where the value lives (`EcsContext` for entities/pools, `GameBuildPass.Run` for creatures/tiers, `WorldSessionBootstrapper` for the streamer; process GC figures are `GaugeTracker.ProcessGauges`). Constant names; a "...Bytes"/"...Milliseconds" suffix sets the unit shown. `Level` for a value, `Cumulative` for a counter (sampled as its change per frame). `read` runs at frame end inside `SystemManager.Update`: it reads a counter its owner keeps, never a pool. With `--diagnostics=gauges` they're sampled every frame (`GaugeTracker`), written per benchmark range (`gauges-*.json`), per report interval (`latest.json`), and shown live in the F3 Diagnostics window (`GaugeHistory`).
- Anything that compares against "every living entity" reads `EcsContext.EntityPopulations` first: the game's split into skeleton-held types (every living entity) and everything else (built entities only). `LeakDetector` compares each pool against the population that can hold it.

## World & Map (Game.World)
- `World : IMapQuery` owns `Map` + placement (`PlaceEntityOnMap`/`MoveEntity`/`RemoveEntityFromMap`).
- `Map`: per-cell stores split per 1024² neighborhood (`MapNeighborhood`; world coordinates in, shift/mask inside) — blocking occupant and occupant index per `(x,y,MapLayer)`, terrain per `(x,y,TerrainLayer)`, structures (walls) per `(x,y,MapLayer)`; terrain and structures are `TerrainCell` flyweights from `TerrainRegistry`. Aura totals per cell are `AuraTotals` (dense chunks per aura per neighborhood, freed at zero); a dense yes/no per cell uses `NeighborhoodBits`. `Map.Bounds` (`Engine.Math.MapBounds`, min inclusive, max exclusive) can start anywhere, negative included, on a neighborhood boundary. The default map is `Map.Unbounded`: whichever neighborhoods are loaded (a dictionary plus a 5x5 lookup grid re-centred with the window), starting with the 3x3 around (0,0); `Bounds` is only the rectangle around them, so test cells with `Contains`. `--map-size=` other than 3072 builds a bounded, fully loaded map with no window. An entity not on the map sits at `TransformComponent.UnplacedOn(layer)`, far outside any map -- never (0,0) or (-1,-1), which are real tiles.
- Map occupancy is governed by `IMapQuery.IsBlocking`, implemented on `World` from two `MultiComponentPool` markers — `ForceBlockingComponent` (wins if present) then `NonBlockingComponent`, else default blocking; both are many-source/count-based so overlapping sources (assumed for all effects) work correctly. `NonBlockingComponent.Kind` (`NonBlockingKind` flags: `Tiny`/`Phasing`) is how `MapWindow` renders the entity while exempt (tiny-grid/phasing-alpha) — folded into the same component that grants the exemption itself (not a separate component), so the two can't drift apart the way they once did. Non-Blocking entities are indexed by position in `Map`'s own `GetNonBlockingEntityIdsAt` (kept in sync by `World`'s placement/move/removal, mirroring the Blocking array) — `MapWindow`, `SelectionWindowContent`, and `AbilityEffectResolver` all query it instead of scanning every non-Blocking entity.
- A system reads a cell's occupants with `IMapQuery.GetOccupantEntityIdSpanAt` (empty off the map, no allocation), never by `foreach` over `GetOccupantEntityIdsAt`, which boxes an enumerator per occupied cell. The span is valid until that cell's occupants change: a reader that runs effects or raises events per occupant copies it first (`ActionEffectResolver`, `ProcessingTierSystem`, `TerrainContactSystem`). The frame's moves are read the same way, through `FrameEventBuffer.ItemSpan`.
- `FloorBuilder`: `CreateMap` builds the Map `GameBootstrapper.Build` takes (the build makes the World over it); `PopulateFloor` needs EntityManager/ComponentManager from Build. Real ordering constraint. A neighborhood is generated in two halves: `TestMapBuilder.Plan` decides it as data (a `NeighborhoodPlan`: layout in its own detached `NeighborhoodLayout` stores, each row's aura-radiating terrain, the spawn list) from its `NeighborhoodRecord` alone -- layout from its seed, population from a per-visit seed -- touching no pool, map or event, so it runs on a worker; the main thread then `Map.LoadNeighborhood(layout)` and spawns the list in order. Startup plans every window neighborhood in parallel and applies them in order. The hallway cross, fixtures, shops and spawn live in neighborhood (0,0) only. At runtime `Game.Floors.NeighborhoodStreamer` (first system in the frame) unloads a neighborhood (destroys its entities, announces its terrain row by row with `TerrainUnloadingEvent`, `Map.UnloadNeighborhood`) and loads one (planned on a worker from the moment it is queued; applied no earlier than `StartDelayFrames` (30) streamer updates later, waiting for the worker if needed, so streaming stays deterministic: load the stores, `TerrainLoadedEvent` per row carrying its aura cells, then population) under a per-frame budget. A load dropped before it starts cancels its worker and counts no population on its record. It drives the sliding window on `WindowShifted` (loads nearest-first, a cache of the 3 most recently dropped neighborhoods, evictions unloaded before loads) and Admin Mode's map context menu "Regenerate". Unloaded cells are off the map: `Map.Contains`/`World.IsOnMap` false, readers empty.

## Blueprints (Game.Blueprints)
- `BlueprintDefinition` = one composable building block: Guid `Id`, `Name`, ordered `Includes` (other definitions by Guid, built first, nested to any depth), an optional `Build` step (`Action<BlueprintContext>`), and facets: `Race` (body plan; grants `RaceSlotsComponent`), `Class` (granted through `ClassEffects`), `Appearance` (`AppearanceFacet`), `NonBlocking`, `Actions`, default `Layer`/`Size`. Rule: what must be known without building goes on the definition; `Build` writes only the per-entity state a build creates. Every blueprint is a `static class` declaring `Id`, `Name` and its whole `Definition` (after the static fields it uses); a build step is its own `private static void Build(BlueprintContext)`, referenced as `Build = Build`, and a pure composition leaves `Build` null. Pure compositions (`Player`, `GoblinForeman`, fixtures) live in `Composites/`; `BlueprintsModule` registers the built-ins. A static step can hold no state: everything a build depends on arrives in `BlueprintContext` (`ComponentManager`, entity id, `Rolls`, `EntityKeys`, seed, registry, action catalog -- what `ActionGrantEffects.Grant` reads an action from), so one method serves every world and every seed.
- `BlueprintRegistry`: session-local `ushort` ids, Guid lookup, re-registering a Guid replaces in place (how a mod replaces a built-in, and every composite including it follows); `Races`/`Classes` are kind views over the one id space. `Resolve` flattens includes depth-first into a cached `ResolvedBlueprint` -- build order (a definition reached twice builds once), races, classes, merged `Actions` (a later grant of an action replaces an earlier one), `EntityAppearance`, occupancy, default layer/size. Cycles, missing includes and nesting past 8 throw; `ResolveAll` runs at the end of module configuration, so a broken mod fails its dry run. Appearance, layer and size: each set field replaces what came before, except a second race's are ignored (a hybrid is its first race). Name = an explicit `Name` if any, else the seeded display name, then each class's name and `NameSuffix`. `Compose(Guid...)` interns an unnamed composite under a Guid derived from its ordered includes.
- To be spawned, a blueprint must resolve a name, description, glyph and a sprite declaration (`AppearanceFacet.NoSprite` = glyph only) -- `ResolvedBlueprint.IsSpawnable`; a trait (Boss, Tiny) doesn't, and is only ever included or applied. These are read from the blueprint through the spawn record (`MapViewQuery`, `EntityNaming`), never stored per entity: `DisplayTextComponent`/`GlyphComponent`/`SpriteComponent` mean a per-instance override (a destroyed container).
- Spawning (Game.Spawning): every entity is spawned by the session's one `EntityFactory` through `Spawn(SpawnRequest)` -- blueprint id and x/y, optionally layer, size, seed, `Crawler` and a reserved id (the player); layer and size default to the blueprint's, seed to the factory's own runtime sequence (population always passes its own). It creates the entity tier-first, builds it (per part in build order: race/class facet, then its `Build`) or defers it to a skeleton, places it, records its spawn move and destroys it if it landed off the map. Every entity carries a `SpawnRecordComponent` (blueprint id, `SpawnFlags`, seed -- 8 B, the flags byte sits in what was padding; Direct pool). Building is in two halves: `BuildSkeleton` writes the skeleton from definitions (see Skeletons below), `BuildComplete` runs every part in build order (race/class facet, then its `Build`), the action-lock stagger, and gives a `SpawnFlags.Crawler` entity its crawler number -- on first build, not at spawn, so an unbuilt crawler never draws one (the allocator has its own sequence seeded from the session seed, so drawing at promotion shifts nothing else). `BuildComplete` reseeds one `SeededRandom` per entity -- a blueprint must draw every random choice from `BlueprintContext.Rolls`, never from a sequence of its own, or the record stops reproducing the entity (`SpawnRecordRebuilder` rebuilds it in a staging world against the session's registry; `SpawnRecordRebuilderTests` guards this). The building itself is `EntityBuilder`'s (definitions, key table, rolls -- no world, tiers or clock), which is what `SpawnRecordRebuilder` uses; `EntityFactory` builds through one and adds placement, tiering, skeletons, spawn moves and crawler numbers.
- `SpawnMoves` (registered first in the frame) records a spawn's move this frame if the moves are still unread, otherwise first thing next frame -- so spawning from a system mid-frame, or from Presentation between frames, is safe. Modules reach the factory as `GameModuleContext.EntityFactory` (built with the context): spawn only once the build is complete, since blueprints resolve after every `Configure`.
- `EntityFactory.Apply(entity, blueprint)` layers a blueprint onto a live entity (a class it gains, a curse): builds a skeleton first, skips any part the entity already has -- one its spawn blueprint built or one applied before -- and records each part it builds as an `AppliedBlueprintComponent` (Multi pool, with its application order). So nothing is ever built onto an entity twice (a merge policy never merges a part into itself; Boss twice doubles health once). Spawn record + applied list = everything the entity was built from: applied parts' actions, class names and name suffixes are read through the list; the rest of an applied part's appearance doesn't change the entity's; the spawn record is untouched. Admin Mode's map context menu offers "Spawn here >" and "Apply >" (`Game.Admin.BlueprintAdminCommands`) -- keep them, they are the in-game test tool.
- `EntityActions` resolves an action from the entity's own `ActionInstanceComponent`, then its applied parts (most recently applied first), then its spawn blueprint's merged grants -- composition's rule, a later part's grant replacing an earlier one. Class slots are not read for actions: every runtime class arrives through `Apply`.
- Skeletons: a creature born into an unsimulated tier is spawned as a skeleton (`CreatureSkeletons`) -- only the types in `EntityFactory.SkeletonComponentTypes`: `TransformComponent`, `ProcessingTierComponent`, `SpawnRecordComponent` and occupancy (`NonBlockingComponent`/`ForceBlockingComponent`). A type goes on that list only if its value is declared on the definition or set by the spawn, and something needs it on unbuilt entities; `BuildSkeleton` writes them from definitions and no build step ever writes one (`BlueprintSkeletonTests`), so the two halves never overlap. The access guard and startup's pool reservation read the same list. Only a blueprint holding a race can be deferred (`ResolvedBlueprint.Deferrable`), so shops, the chest and the test dummy are always built at spawn. It is built (`EnsureBuilt`) on `ProcessingTierEvents.TierChanging` into a simulated tier -- before any `TierChanged` handler -- and must be built by any other gameplay read or write that reaches it; it is never returned to a skeleton. Presentation never builds one: `MapViewQuery` draws/names it from its blueprint's appearance and seed, inspection shows `SpawnRecordRebuilder`' rebuild labelled "Unsimulated". In Debug, `SkeletonAccessGuard` (via `IEntityAccessGuard` on every other pool) throws when the simulation (`SystemManager.IsUpdating`) touches a pool a skeleton doesn't hold -- a missed build fails loudly instead of reading as "no loot". A build's spawn move goes through `SpawnMoves` -- usually next frame, since the tier drain runs after this frame's moves were read. Promotions wait for evicted neighborhoods' built creatures to be destroyed (`ProcessingTierResolver.PromotionsHeld` = `NeighborhoodStreamer.IsEvictingBuiltCreatures`, which runs evictions' built creatures ahead of other work), so builds reuse their storage.

## Presentation
- `PresentationBootstrapper`: fixed service set (FontService, SpriteBatchRenderer, LabelRenderer, TileRenderer, WindowService) — no module system (set is static).
- UI: `Window`/`WindowService`/`MapWindow`, content panes (`InspectionWindowContent`, `DebugWindowContent`). `NotificationCenter` can block gameplay update for a frame (checked in `GameLoop.Update` before `EcsContext` advances).
- **Presentation never touches the store.** It reads through `GameSession.Views` and writes through `GameSession.Commands`; no Presentation type may name `ComponentManager`, `EntityManager` or a component pool (component values are fine -- views hand them back). `PresentationStoreAccessArchitectureTests` scans the whole assembly; the only exemptions are `InspectionWindowContent` and `DiagnosticsWindow`. Pure arithmetic that reads no pool (shop price bands, scroll scaling, `InventoryQueries.TryResolveEffectiveItem`) is called directly. A game rule a UI gesture triggers reaches Game as a command call or an event (`AchievementNotificationDismissedEvent` -> `AchievementModule`), and the rule lives in its module.
- Shell composition: `ShellServices` (layers, `MapViewState`, camera, context menu, tooltip, `PointerState`, cursor text) goes only to composition points (`ElementFactoryRegistry`, `ItemWindowCoordinator`); an element takes the specific services it uses. `PointerState` is what `UiInputController` publishes at the end of each update for content drawn at the cursor. `ItemWindowCoordinator` builds the inventory/loot/shop/trade/Item Details/comparison/loot-box-results controllers and owns the rules between them (loot and shop mutually exclusive, trade follows shop, item clicks go to comparison when armed, `ReleaseEntity` on destroy). The item windows, grid and currency row share one `InventoryServices` record. Admin Mode's commands are `Game.Admin.AdminTools`, offered through `AdminContextMenuOptions`.
- Core design principles: remove ambiguity, remove unexpected actions. When an interaction could mean more than one thing (e.g. a drag with no single underlying identity to act on), don't guess — either resolve it to something concrete first, or refuse it outright with clear feedback (a disabled cursor, a no-op) rather than doing something the player didn't ask for.

## Scale
`GameLoop.InitialEntityCapacity` sized for TestMapBuilder's default 3072×3072×3 map, a 3×3 of 1024² neighborhoods (~660k entities; terrain and walls are flyweight cells in `Map`, not entities — see `Game/Terrain`) — not an arbitrary default; it sizes Direct pools. Packed/Multi pools index entities through pages (`EntityPages`, 1024 ids per page, allocated on first write), so a rare pool costs only the id ranges its holders fall in, and their dense storage starts at `InitialComponentCapacity` (small) or a registration's own `initialCapacity` and grows ×1.5 (`DenseCapacityGrowth`). `WorldSessionBootstrapper` also reserves the window's settled population before the first frame: (9 + cache 3) / 9 of the startup one, plus 10%, for what every creature holds (skeleton components), and 3 built neighborhoods' worth (x3.3 of the startup built population) for everything else -- without it, each early window shift resized the largest pools mid-drain (one 30-60 ms frame each). Population speed across a shift is bounded by gen-1 GC pauses, which track what each creature allocates and keeps: share immutable definitions (overrides, loot) instead of building one per creature.
